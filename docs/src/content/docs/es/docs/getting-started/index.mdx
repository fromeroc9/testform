# Instalacion y Quickstart

Aprende a instalar Testform globalmente, inicializar tu espacio de trabajo y comprender el ciclo de vida del estado segun el tipo de backend configurado.

## Requisitos Previos

Antes de comenzar, asegurate de contar con:
- **Node.js:** version 18.0.0 o superior instalada (`node -v`).
- **Git:** repositorio Git inicializado en tu espacio de trabajo (`git status`).
- **NPM:** gestor de paquetes para instalar el binario global de Testform.

## Paso 1: Instalacion Global

Testform es una herramienta de linea de comandos (CLI) que se instala **unicamente de forma global** en tu sistema operativo, al igual que herramientas como Terraform o Git:

```bash
npm install -g @fromeroc9/testform
```

Verifica la instalacion consultando la version del binario:

```bash
testform -version
```

Salida esperada en terminal:

```text
Testform v1.0.17
on win32_x64
```

> Testform consulta automaticamente el registro de NPM para comprobar si existe una version mas reciente. Si tu CLI esta desactualizada, mostrara un aviso similar al de Terraform:
> ```text
> Your version of Testform is out of date! The latest version
> is 1.18.0. You can update by running:
>   npm install -g @fromeroc9/testform
> ```

## Paso 2: Inicializar el Proyecto (testform init)

Ejecuta el comando `testform init` en la raiz de tu repositorio:

```bash
testform init
```

Salida real en consola:

```text
Initializing the backend...
Initializing Testform configuration...
- Configuration: main.yml (v1.0)
- State backend: ready

Testform has been successfully initialized!

You may now begin working with Testform. Try running "testform plan" to see
any changes that are required for your test management resources.

If you ever set or change configuration for Testform, rerun this command to
reinitialize your working directory.
```

### Ciclo de Vida en Backend Local (`backend: local`)

Cuando utilizas el backend local por defecto, los archivos de estado se crean dinamicamente segun la fase del flujo de trabajo:

1. **Tras `testform init`:**
   - Unicamente existe `main.yml`. No se crea `testform.state` ni copias de respaldo.
2. **Durante `testform plan`:**
   - Si `testform.state` aun no existe, Testform lee un estado vacio en memoria (0 recursos) y calcula las adiciones planeadas (`+ create`) en modo de solo lectura, sin escribir nada en disco.
3. **Tras el primer `testform apply`:**
   - Al aplicar los recursos con exito, se crea por primera vez `testform.state` con `serial: 1` y los metadatos de los casos conciliados. No se crea archivo `.backup` porque no habia un estado previo que respaldar.
4. **A partir del segundo `testform apply`:**
   - Antes de modificar el estado, Testform copia el estado previo a `testform.state.backup` (`serial: 1`) y escribe el nuevo estado en `testform.state` (`serial: 2`). Ambos archivos comparten exactamente el mismo formato JSON.

```text
mi-proyecto/
â”œâ”€â”€ main.yml            # Manifiesto principal de configuracion
â”œâ”€â”€ testform.state          # Estado activo (creado tras el primer apply)
â””â”€â”€ testform.state.backup   # Respaldo automatico (creado a partir del segundo apply)
```

### Ciclo de Vida en Backends Remotos (`s3`, `oci`, `azurerm`, `gcs`)

Cuando configuras un backend en la nube en tu `main.yml`:

```text
mi-proyecto/
â””â”€â”€ main.yml            # Manifiesto principal de configuracion
```

- **Sin archivos de estado locales:** En ningun momento se generan archivos `testform.state` ni `testform.state.backup` en tu disco local.
- **Persistencia en la Nube:** Las operaciones de lectura y escritura (`s3.putObject`, `UploadBlob`, etc.) se comunican de forma directa y atomica con el bucket remoto.
- **Repositorio Git Limpio:** Tu espacio de trabajo queda 100% libre de archivos de estado locales, previniendo conflictos en Pull Requests y filtraciones de credenciales.
- **Respaldos Nativos:** La recuperacion ante desastres y el historial de cambios se gestionan con el Versionado de Objetos nativo (*Bucket Versioning*) del proveedor cloud.
