# Modular Architecture (@module)

Testform implements a full-featured modular system with functional parity to Terraform modules, allowing you to package, parameterize, and reuse test workflows across Gherkin and YAML.

---

## 1. The Code Duplication Problem in QA

Essential test workflows—such as authentication, cart preparation, or initial navigation—are repeatedly copied across dozens of feature files. Copy-pasting these steps manually leads to brittle test suites and violates the DRY (Don't Repeat Yourself) principle.

With **Testform Modules**, you can encapsulate complete workflows or specific test scenarios and dynamically compose them with input parameters (`vars`) and return values (`outputs`).

---

## 2. Declaring a Module

### A. Module in a Feature File (`.case.feature`)

Create a reusable module file under `modules/auth/login.case.feature`:

```gherkin
@testcase
Feature: Authentication Module
  @tc-login
  Scenario: Login with credentials
    Given the user navigates to "<base_url>"
    When entering username "<user>" and password "<password>"
    Then the session is active with role "<role>"
```

Steps can use angle brackets `<param>` or variable syntax `${var.param}`, which are dynamically replaced when the module is invoked.

### B. Declaration in `testform.yml`

You can centrally register reusable modules with their default variables:

```yaml
modules:
  auth_standard:
    source: "./modules/auth/login.case.feature"
    vars:
      base_url: "${var.app_url}"
      user: "standard_user"
      password: "${var.default_password}"
      role: "viewer"
    outputs:
      session_id:
        value: "${testrun.modules/auth/login.case.feature.@tr-1.issueNumber}"
```

### C. Remote Modules (Git Registry)

Testform supports remote Git repositories to share modules across teams or organizations:

```yaml
modules:
  auth_shared:
    source: "git::https://github.com/my-org/qa-modules.git//auth?ref=v1.2.0"
    vars:
      base_url: "https://staging.company.com"
```

During `testform init`, remote modules are automatically downloaded to `.testform/modules/`.

## 3. Invocation and Input Parameters (`vars`)

### A. Direct Invocation with `vars`

Invoke the module while supplying specific input parameters:

```gherkin
@tc-checkout-admin
@module(source="./modules/auth/login.case.feature", vars={user: "admin", role: "superuser"})
Scenario: Checkout executed with administrative credentials
  When the user clicks "Confirm Payment"
  Then the transaction is approved
```

The parameters declared in `vars={...}` replace `<user>` and `<role>` in the inherited steps before scenario execution.

### B. Invocation by Module Name

If the module is registered in `testform.yml`, you can invoke it directly by name or override variables:

```gherkin
@tc-checkout-standard
@module("auth_standard")
Scenario: Checkout with standard user
  When the user clicks "Confirm Payment"
  Then the transaction is approved
```

Or with variable overrides:

```gherkin
@tc-checkout-custom
@module(name="auth_standard", vars={user: "custom_qa_user"})
Scenario: Checkout with custom QA user
  When the user clicks "Confirm Payment"
  Then the transaction is approved
```

### C. Selecting a Specific Scenario

If a module feature file contains multiple scenarios, select only the one you need using `scenario` or dot notation:

```gherkin
# Option 1: scenario argument
@module(source="./modules/auth/login.case.feature", scenario="@tc-login", vars={user: "demo"})

# Option 2: Canonical dot notation
@module(source="./modules/auth/login.case.feature.tc-login", vars={user: "demo"})
```

## 4. Strict Output Scoping (`${module.<name>.<output>}`)

> **Isolation Rule:** Outputs defined inside a module belong **strictly to the module's namespace** and do not pollute the global scope.

### A. Module Declaration

Inside `modules/auth/outputs.yml`:

```yaml
outputs:
  session_token:
    description: "Session token generated by authentication workflow"
    value: "tok_secure_active_session"
  user_id:
    value: "${testcase.modules/auth/login.case.feature.@tc-login.remoteId}"
```

### B. Consumption from Root Project

The root project or any consuming scenario references the output using the `module.<name>.<output>` prefix:

```yaml
# testform.yml
outputs:
  active_admin_token:
    description: "Session token from auth module"
    value: "${module.auth.session_token}"
```

And in Gherkin test steps:

```gherkin
Scenario: Authenticated operation
  When executing operation with token "${module.auth.session_token}"
```

