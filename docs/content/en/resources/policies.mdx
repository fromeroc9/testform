# Policy Engine and Validation (Policies)

Testform incorporates a static analysis and declarative governance engine similar to tools like Open Policy Agent (OPA) or HashiCorp Sentinel in the IaC ecosystem.

Before applying any remote changes with `testform plan` or `testform apply`, the `testform validate` command inspects all feature files to certify compliance with project quality standards.

---

## 1. The 7 Built-in System Policies

Testform comes with 7 built-in system policies active by default:

| Policy ID | Scope | Severity | Purpose & Business Rule |
| :--- | :--- | :--- | :--- |
| **`identity-required`** | `testcase`, `testrun`, `testplan` | `error` (Blocking) | **Active by default.** Requires a valid identity tag (`@tc-1` on `testcase` scenarios, `@tr-1`/`@tp-1` at `Feature:` level for `testrun` and `testplan`). This is essential so that `testruns` can accurately reference cases via `Rule: file.case.feature -> Scenario: @tc-id`. |
| **`identity-unique`** | `testcase`, `testrun`, `testplan` | `error` (Blocking) | Ensures identities do not collide. Within `testcase`, identities must be unique per file; within `testrun` and `testplan`, they must be globally unique across the workspace. It automatically suggests the next available index (e.g. `@tc-4`). |
| **`required-gherkin`** | `testcase` | `error` (Blocking) | Mandates that every Feature has a name, every Scenario has a name, and all three BDD step types (`Given`, `When`, `Then`) are declared. |
| **`no-feature-tags`** | `testcase`, `testrun`, `testplan` | `error` (Blocking) | Forbids arbitrary tags at the `Feature:` level. Only the scope tag (`@testcase`, `@testrun`, `@testplan`) and the corresponding identity tag are allowed on `Feature:`. All other tags must be placed on the `Scenario:` level. |
| **`required-fields`** | `testcase`, `testrun`, `testplan` | `error` (Blocking) | Verifies that any field defined with `required: true` in `testform.yml` is provided in the scenario using DSL steps (e.g. `* priority = "High"`). |
| **`undeclared-fields`** | `testcase` | `warning` (Informational) | Warns when a scenario assigns a DSL field not declared in the `fields` section of `testform.yml`. |
| **`duplicate-testruns-in-testplan`** | `testplan` | `error` (Blocking) | Prevents the same `testrun` file from being duplicated within a single `testplan` or across separate concurrent testplans. |

## 2. Deep Dive: `identity-required` Policy

The `identity-required` policy protects the integrity of the test lifecycle:

```gherkin
# ❌ Policy Violation: Scenario missing identity tag
@testcase
Feature: User Authentication
  Scenario: Login with valid credentials
    Given the user is on "/login"
    When entering valid credentials
    Then the dashboard is displayed

# Error output:
# ╷ Error: Every scenario must have an identity tag matching the configured identity pattern.
# │ Add the identity tag (e.g. @tc-1) to each scenario.
```

```gherkin
# ✅ Correct: Explicit identity tag assigned
@testcase
Feature: User Authentication
  @tc-1
  Scenario: Login with valid credentials
    Given the user is on "/login"
    When entering valid credentials
    Then the dashboard is displayed
```

### Why is this mandatory for `testruns`?
In Testform, execution cycles (`*.run.feature`) bind testcases by specifying their source rule and identity:

```gherkin
@testrun @tr-smoke-1
Feature: Smoke Test Run

  Rule: auth.case.feature
    Scenario: @tc-1
      * link status = passed
```

Without the `@tc-1` tag in the source file, the test execution engine cannot resolve which remote Issue owns the result, making it impossible to produce checklists and comments on GitHub or GitLab.

## 3. Extending Policies (Custom Policies)

Quality Engineering teams can register custom policies using TypeScript files.

### Registration via `registerPolicy`:

```typescript
import { registerPolicy } from '@fromeroc9/testform';

registerPolicy({
    id: "max-steps-limit",
    scope: ["testcase"],
    action: (scenarios, rules, scope) => {
        for (const scenario of scenarios) {
            if (scenario.steps.length > 10) {
                rules.push({
                    id: "max-steps-limit",
                    type: "warning",
                    title: `Scenario "${scenario.name}" exceeds the 10-step limit.`,
                    detail: "Consider refactoring the scenario into higher-level business steps.",
                    uri: scenario.uri,
                    scenario: scenario.name,
                    line: scenario.location
                });
            }
        }
    }
});
```

## 4. Extending Resources (Resource Registry)

Testform allows customizing or registering new declarative resource types by defining how fields and execution comments map to remote providers:

```typescript
import { resource } from '@fromeroc9/testform';

resource.registry({
    type: 'custom_testcase',
    fields: [
        { name: 'title', value: (s) => s.name },
        { name: 'body', value: (s) => s.description || '' },
        {
            name: 'labels',
            value: (s) => s.tags?.map(t => t.replace('@', '')) || []
        }
    ],
    comments: (s, context) => {
        return [{
            identity: s.custom?.identity,
            status: 'pending',
            body: 'Testcase initialized via custom resource adapter'
        }];
    }
});
```
