# Gherkin as Test-as-Code

Gherkin is traditionally known as a business-readable Domain Specific Language (DSL) used for Behavior-Driven Development (BDD).

In **Testform**, Gherkin serves a dual purpose:
1. **Behavior Specification**: Readable by product owners, QA analysts, and automation engineers.
2. **Declarative Configuration Language**: The code compiled by Testform to provision, update, and manage cloud testing resources.

---

## Why Gherkin Instead of HCL or YAML?

| Feature | YAML / HCL Test Definitions | Gherkin in Testform |
| :--- | :--- | :--- |
| **Executable Specification** | Requires custom parsers or separate test code. | Natively executable by Cucumber, Behave, Playwright, and Cypress. |
| **Business Readability** | Difficult for non-developers to read and review. | Universal language understood by technical and business stakeholders. |
| **Version Controlled** | Yes (`git`). | Yes (`git`). Every scenario change goes through Pull Requests. |
| **Tooling & IDE Support** | Generic YAML validation. | Rich syntax highlighting, step auto-completion, and formatting tools. |

---

## How Testform Compiles Gherkin

When Testform parses a `.feature` file, it constructs a complete Abstract Syntax Tree (AST):
- **Feature Headers**: Converted to resource groupings, descriptions, and global labels.
- **Background Blocks**: Converted to shared attributes, defaults, and preconditions.
- **Scenario Blocks**: Converted into individual resource units (e.g., `github_testcase`).
- **Rule Blocks**: Converted into dependency relationships and execution sets (e.g., `github_testrun`).
- **Tags (`@tag`)**: Converted into Provider labels and category filters.
- **Step Variables (`* key = value`)**: Extracted into typed custom fields.
