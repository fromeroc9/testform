# Best Practices for Test-as-Code

Writing test cases as declarative code requires a disciplined mindset to keep tests robust, readable, and maintainable across large engineering organizations.

---

## 1. Keep Scenarios Atomic and Independent

Each scenario should test **one specific behavior** or business rule.
- ❌ **Anti-pattern**: A single 30-step scenario that logs in, changes profile settings, searches for a product, purchases it, and leaves a review.
- ✅ **Best Practice**: Separate atomic scenarios:
  1. `Scenario: @tc-1 Update user profile photo`
  2. `Scenario: @tc-2 Search product by exact SKU`
  3. `Scenario: @tc-3 Checkout with credit card`

*Why?* Atomic scenarios make it crystal clear which feature broke when a regression test fails, and each scenario maps cleanly to a dedicated issue.

---

## 2. Always Use Identity Tags (`@tc-*`, `@tr-*`, `@tp-*`)

Never leave scenarios without an identity tag in production repositories.
```gherkin
# Good
@smoke @tc-1
Scenario: User views active subscription

# Bad (renaming this scenario will orphan the previous GitHub Issue)
@smoke
Scenario: User views active subscription
```

Run `testform validate` in CI to enforce the `identity-required` policy across pull requests.

---

## 3. Keep Code DRY with `Background:`

Avoid repeating the same milestone, assignees, or setup steps in every scenario:

```gherkin
Feature: Order Management

  # Common metadata and setup defined ONCE:
  Background:
    * milestone = "Sprint 42"
    * assignees = "qa-orders"
    Given an authenticated customer with an active cart

  @tc-1
  Scenario: Standard credit card checkout
    When the customer submits valid card details
    Then the order is confirmed

  @tc-2
  Scenario: PayPal express checkout
    When the customer selects PayPal
    Then the order is confirmed
```

---

## 4. Run `testform fmt` Before Every Commit

Consistent indentation and alignment makes code reviews significantly faster. Testform provides a canonical formatter:

```bash
testform fmt
```

You can add `testform fmt -check` as a Git pre-commit hook or CI check to ensure all feature files adhere to standard styling.
