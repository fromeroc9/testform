# Mejores Prácticas para Test-as-Code

Gestionar casos de prueba como código declarativo requiere disciplina y buenas prácticas para mantener la suite robusta, legible y escalable en equipos de ingeniería de gran escala.

---

## 1. Mantén los Escenarios Atómicos e Independientes

Cada escenario debe verificar **un único comportamiento** o regla de negocio bien delimitada.
- ❌ **Antipatrón**: Un escenario de 30 pasos que inicia sesión, modifica ajustes de perfil, busca un producto, lo compra y publica una reseña.
- ✅ **Mejor Práctica**: Escenarios atómicos separados:
  1. `Scenario: @tc-1 Actualizar foto de perfil del usuario`
  2. `Scenario: @tc-2 Buscar producto por código SKU exacto`
  3. `Scenario: @tc-3 Pagar pedido con tarjeta de crédito`

*¿Por qué?* Los escenarios atómicos permiten identificar con total certeza qué funcionalidad falló ante una regresión, y cada uno se asocia limpiamente con su propio issue.

---

## 2. Utiliza Siempre Etiquetas de Identidad (`@tc-*`, `@tr-*`, `@tp-*`)

Nunca dejes escenarios sin etiqueta de identidad permanente en repositorios productivos.
```gherkin
# Correcto
@smoke @tc-1
Scenario: El usuario consulta su suscripción activa

# Incorrecto (renombrar este escenario dejará huérfano el Issue anterior en GitHub)
@smoke
Scenario: El usuario consulta su suscripción activa
```

Ejecuta `testform validate` en tu pipeline de CI para exigir el cumplimiento estricto de la política `identity-required` en los pull requests.

---

## 3. Evita Duplicación (DRY) Utilizando `Background:`

No repitas el mismo hito (milestone), asignados o pasos de preparación en cada escenario:

```gherkin
Feature: Gestión de Pedidos

  # Configuración común definida UNA SOLA VEZ:
  Background:
    * milestone = "Sprint 42"
    * assignees = "qa-pedidos"
    Given un cliente autenticado con un carrito de compras activo

  @tc-1
  Scenario: Pago estándar con tarjeta de crédito
    When el cliente envía los datos válidos de la tarjeta
    Then el pedido queda confirmado

  @tc-2
  Scenario: Pago express mediante PayPal
    When el cliente selecciona la opción de PayPal
    Then el pedido queda confirmado
```

---

## 4. Ejecuta `testform fmt` Antes de Cada Commit

Una indentación y alineación consistentes facilitan y agilizan las revisiones de código en los Pull Requests. Testform proporciona un formateador canónico:

```bash
testform fmt
```

Puedes configurar `testform fmt -check` como un hook pre-commit de Git o como un paso obligatorio en tu flujo de CI para garantizar que todos los archivos `.feature` cumplan con las reglas de estilo estándar.
